# SECTION 1: Tekla Open API Limitations

Tekla Open API provides robust programmatic access to 3D geometry and databases, but for production-scale 2D fabrication drawing generation, it possesses significant architectural constraints.

### 1.1 Single-Threaded Apartment (STA) & COM Marshaling Bottleneck
* **Technical Detail:** The .NET Open API libraries (`Tekla.Structures.dll`, `Tekla.Structures.Model.dll`, `Tekla.Structures.Drawing.dll`) are managed wrappers around legacy native C++ unmanaged COM/RPC servers.
* **Limitation:** All Open API calls must execute within a Single-Threaded Apartment (`[STAThread]`).
* **Failure Mode:** Attempting to parallelize drawing queries or generation using `Parallel.ForEach`, `Task.Run`, or PLINQ results in fatal COM marshaling exceptions:
  ```text
  System.Runtime.InteropServices.COMException (0x8001010E):
  The application called an interface that was marshalled for a different thread. (RPC_E_WRONG_THREAD)
  ```
* **Performance Impact:** Processing 700 precast elements cannot utilize multi-core server processors natively; execution is strictly serial.

---

### 1.2 Mandatory Active Drawing Lock (`SetActiveDrawing`) & Memory Leaks
* **Technical Detail:** In the Drawing API, reading visual geometry, accessing view coordinates, modifying leader lines, or editing view-level objects requires loading the drawing into the active UI state:
  ```csharp
  DrawingHandler drawingHandler = new DrawingHandler();
  drawingHandler.SetActiveDrawing(drawing, false); // false = do not ask save prompt
  ```
* **Limitation:** Opening and closing drawings in a loop does not fully release internal unmanaged C++ view buffers, GDI handles, and OpenGL textures.
* **Failure Mode:** After processing approximately 150–250 consecutive drawings, memory consumption climbs to 8–12 GB RAM, leading to:
  ```text
  System.OutOfMemoryException: Insufficient memory to continue the execution of the program.
  ```
* **Latency:** Each `SetActiveDrawing` call incurs a 1.5 to 4.0-second GUI rendering latency, making 1000 drawings take up to 2 hours purely in open/close overhead.

---

### 1.3 3D Global to 2D Drawing View Coordinate Drift
* **Technical Detail:** Mapping 3D model vertices $(X, Y, Z)$ into 2D drawing view plane points $(x, y)$ requires calculating transformation matrices via `View.DisplayCoordinateSystems`:
  $$\mathbf{P}_{\text{view}} = \mathbf{M}_{\text{view}} \times \mathbf{P}_{\text{global}}$$
* **Limitation:** When dealing with precast elements with skewed cuts, architectural reveals, chamfers, or inclined corbels, the projected bounding box generated by the API frequently drifts from the actual solid silhouette.
* **Failure Mode:** Dimensions placed via Open API snap to incorrect phantom vertices or offset outside the physical boundary of the cast unit.

---

### 1.4 Point Snapping & Associativity Breakdown ("Red Dimensions")
* **Technical Detail:** When inserting a `StraightDimensionSet`, the Open API requires an explicit `PointList` with points snapped directly to physical part vertices.
* **Limitation:** If a model undergoes subsequent modifications (re-numbering, solid recalculation, or minor parametric adjustment), the associative linkage between the 2D dimension and the 3D solid edge breaks.
* **Failure Mode:** The drawing canvas renders "Red Dimensions" (unassociated dimension marks), which invalidate automated shop drawing generation and require manual drafter intervention.

---

### 1.5 No Native Headless Execution for Drawings
* **Technical Detail:** While the Model API can run in semi-headless mode (console application without UI dialogs), the Drawing API requires an active desktop window session.
* **Limitation:** You cannot run automated drawing extraction inside standard Windows Services, headless Docker containers, or background Azure/AWS task runners without an active GUI user session logged into Windows.

# SECTION 2: Tekla Macros (Akit Scripting) Limitations

Tekla Macros use the proprietary **Akit** engine to record and replay user interface interactions. While valuable for simple repetitive tasks, macros are dangerous for mission-critical automation pipelines.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                          AKIT MACRO EXECUTION LOOP                          │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   [Akit Script] ───► [Simulated UI Click] ───► [Tekla Modal Dialog Opens]   │
│                             │                                  │            │
│                             ▼                                  ▼            │
│                   No Return Status / Payload       Requires Screen Focus    │
│                   (Silent Success / Failure)      (Crashes if Minimized)    │
│                             │                                  │            │
│                             ▼                                  ▼            │
│                      [Execution Hang]               [Version Drift Break]   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 2.1 Complete Absence of Return Codes and Status Feedback
* **Limitation:** Akit commands are purely fire-and-forget:
  ```csharp
  akit.Callback("acmdOpenDrawingList", "", "main_frame");
  akit.ValueChange("dia_drawings_catalog", "v_filter", "precast_walls");
  ```
* **Impact:** The macro cannot return a `bool`, `int`, or JSON payload. If the drawing creation fails (e.g., due to duplicate numbering, licensing error, or missing template), the macro continues blindly to the next step.
* **Consequence:** Batch pipelines report 100% completion even when 0 drawings were actually generated.

---

### 2.2 Strict UI Focus, Screen Resolution & Window State Dependency
* **Limitation:** Akit executes by injecting mouse and keyboard events into the OS message queue.
* **Failure Modes:**
  1. **Minimized Window:** If the Tekla Structures window is minimized or loses focus to another application, Akit commands are swallowed or delivered to wrong windows.
  2. **Screen Resolution Drift:** Macros recorded on a $1920 \times 1080$ screen frequently fail on a $4\text{K}$ display or headless remote desktop with different DPI scaling.
  3. **Screen Lock:** If Windows locks due to inactivity (screensaver/idle policy), the macro engine freezes permanently.

---

### 2.3 Fragility to Version Upgrades and Localization
* **Limitation:** Macros rely on hardcoded internal dialog control names (e.g., `dia_drawings_catalog`, `push_button_apply`).
* **Failure Modes:**
  * **Version Updates:** Moving from Tekla 2024 to 2026 often deprecates or renames internal control IDs without notice.
  * **Language Packs:** If an environment switches from English to German, French, or Japanese, button label hooks and localization strings break the macro execution entirely.

---

### 2.4 Lack of Exception Handling (`try / catch` Inability)
* **Limitation:** You cannot wrap an Akit macro command block in a C# `try-catch` construct to catch graphical crashes.
* **Impact:** If Tekla opens an unexpected modal dialog (such as *"Numbering is not up to date. Continue?"*), the macro cannot detect or dismiss it. The automated batch pipeline hangs indefinitely waiting for a human click.

# SECTION 3: Template Editor (`.tpl`) Limitations

Tekla Template Editor is the native engine responsible for rendering Title Blocks, Bills of Materials (BOM), Rebar Bending Schedules (BBS), and general drawing tables.

### 3.1 Total Absence of Dynamic Table Pagination
* **Limitation:** Template Editor designs assume a fixed rectangular region on the drawing sheet.
* **Failure Mode:** When detailing heavily reinforced precast members (such as seismic shear walls with 50+ unique rebar mark types and varied bending shapes), the table rows exceed the available sheet height.
* **Consequence:** The table physically overflows off the bottom of the drawing border or collides with the title block. Tekla **cannot** natively split an overflowing table onto a "Sheet 2 of 2".

---

### 3.2 Lack of Dynamic Column Wrapping
* **Limitation:** A table cannot dynamically sense that it has reached vertical capacity and wrap remaining items into an adjacent column (Multi-column flow).
* **Workaround Attempt:** Detailers attempt complex conditional row visibility (`GetFieldFormula`, `StepValue`), but this requires hardcoding maximum row assumptions, which breaks whenever a unique element exceeds that fixed limit.

---

### 3.3 Primitive Formula & String Manipulation Language
* **Limitation:** The Template Editor formula syntax is based on an ancient, highly constrained syntax.
* **Constraints:**
  * **No Regular Expressions (Regex):** String parsing (extracting project codes, mark prefixes) requires clumsy nested `mid()`, `left()`, `find()` statements.
  * **No Array / Set Operations:** You cannot perform distinct grouping, array sorting, or LINQ-style filtering natively within a table cell.
  * **No External Data Source Calls:** Templates cannot query external databases, REST APIs, or local JSON files for dynamic hardware specs.

---

### 3.4 Distortion in Graphical Rebar Bending Sketches
* **Limitation:** Displaying rebar shapes inside BBS tables uses the native `DIM_A`, `DIM_B`, `DIM_C` graphical shape generator.
* **Failure Mode:** The graphical shape generator forces complex 3D non-standard bent bars, multi-planar ties, and helical spirals into a fixed aspect-ratio cell.
* **Consequence:** Dimensions clip outside table boundaries, overlap neighboring cells, or display illegible font sizes.

---

### 3.5 Nested Hierarchy Performance Degradation
* **Limitation:** In complex assemblies where tables iterate across multiple nested levels:
  $$\text{CAST\_UNIT} \longrightarrow \text{ASSEMBLY} \longrightarrow \text{PART} \longrightarrow \text{REBAR} \longrightarrow \text{MODIFIER}$$
* **Impact:** Every open and pan action in the drawing requires the Template Editor to perform synchronous recursive tree walks, causing extreme UI lag on large models.

### Implementation Strategy:

1. **Decouple Data from Geometry:**
   Do not rely on Tekla `.tpl` tables to calculate BOM or BBS schedules. Extract structured JSON data directly from the 3D model using Open API.
2. **Dynamic Multi-Page Vector Assembly:**
   Use modern PDF engines (`PyMuPDF` or `QuestPDF`) to take the raw graphical views from Tekla and combine them with dynamically paginated, vector-perfect BBS and BOM tables.
3. **Out-of-Process Worker Recycling:**
   Wrap the Tekla Open API in an isolated CLI/worker process that automatically kills and restarts itself every 25–50 drawings to prevent GDI and COM memory leaks:
   ```csharp
   // Enforce clean release of unmanaged COM pointers
   if (drawing != null) {
       drawingHandler.CloseActiveDrawing(false);
       Marshal.ReleaseComObject(drawing);
   }
   GC.Collect();
   GC.WaitForPendingFinalizers();
   ```
4. **Automate Zero-Missing Validation:**
   Enforce model numbering and comprehensive object iteration prior to drawing creation to guarantee zero missed pieces:
   ```csharp
   if (model.GetProjectInfo() != null) {
       model.PerformNumbering();
   }
   var castUnits = model.GetModelObjectSelector()
                        .GetAllObjectsWithType(ModelObject.ModelObjectEnum.CAST_UNIT);
   ```
